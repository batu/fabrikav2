# Detecting Small Cartoon Birds in 4096px Illustrations: Detector Landscape

Target: 15-25 flat-color/line-art birds per 4096x4096 hidden-object scene, each ~100-250px (2-6% of image width), on a single RTX 4090, fully offline, deterministic given pinned weights. This survey compares open-vocab zero-shot detectors, tiling strategy, small-dataset YOLO fine-tuning, and exemplar-based few-shot approaches, with every non-obvious claim traced to a primary source.

## Try first on the 4090 (ranked shortlist)

**1. SAHI-tiled Ultralytics YOLO fine-tune (recommended primary path).** Auto-label a seed set with an open-vocab detector (below), hand-correct, then fine-tune `yolov8n` or `yolov8s` (or `yolo11n`/`yolo11s`) on crops. Serve with [SAHI](https://github.com/obss/sahi), which has native Ultralytics integration ([SAHI quick-start docs](https://obss.github.io/sahi/quick-start/), [Ultralytics SAHI guide](https://docs.ultralytics.com/guides/sahi-tiled-inference)). `pip install ultralytics sahi`. Gotcha: Ultralytics' own dataset-size guidance (1,500 images/class, 10k instances/class — [Ultralytics model-training-tips docs](https://docs.ultralytics.com/guides/model-training-tips)) is far above "a few hundred images," so expect to lean on augmentation and accept the model will need active-learning-style correction rounds, not one clean training run.

**2. GroundingDINO (open-vocab) + SAHI, zero training required, as the auto-labeler or a fallback detector.** Repo: [IDEA-Research/GroundingDINO](https://github.com/IDEA-Research/GroundingDINO), Apache-2.0-licensed weights hosted on Hugging Face (`IDEA-Research/grounding-dino-tiny` / `-base` via `transformers`), no account/gating required for the base checkpoints. `pip install groundingdino-py` or use via `transformers`. SAHI lists native support only for Ultralytics/MMDetection/Detectron2/HF/TorchVision/RT-DETR/YOLO-World — GroundingDINO isn't in that native list, so tiling it means slicing images and merging boxes manually (SAHI's generic "any model" path, not a first-class integration). Gotcha: trained at 800px shortest-edge / 1333px longest-edge ([GroundingDINO inference.py `RandomResize([800], max_size=1333)`](https://github.com/IDEA-Research/GroundingDINO/blob/main/groundingdino/util/inference.py), confirmed in [issue #158](https://github.com/IDEA-Research/GroundingDINO/issues/158)), so for a 4096px scene with 100-250px birds, tiles of roughly 800-1024px with 20-25% overlap keep birds near the model's native scale (SAHI's own quick-start example uses 512px tiles at 20% overlap as a baseline — [SAHI docs](https://obss.github.io/sahi/quick-start/)).

**3. YOLO-World as a faster open-vocab alternative, with a license caveat.** Repo: [AILab-CVC/YOLO-World](https://github.com/AILab-CVC/YOLO-World), pretrained weights and logs provided directly in the repo, and it is one of SAHI's natively-integrated frameworks. Verify the license file at fetch time — recent search results are inconsistent (GPL-v3 vs. a sibling AGPL-3.0 project, YOLOE); pin and record the exact `LICENSE` file text from the checkpoint's source commit before use in anything beyond internal tooling.

No published benchmark was found showing any of these hold up on flat-cartoon/line-art domain out of the box — treat step 1's fine-tune, not zero-shot open-vocab detection, as the thing that actually has to work.

## 1. Open-vocabulary detector transfer to cartoon/illustration domains

No primary-source paper or model card was found that evaluates GroundingDINO, OWLv2, YOLO-World, Florence-2, or DETIC specifically on a cartoon/comics/anime/illustration object-detection benchmark. This is a genuine gap, not an oversight in searching — this is stated explicitly rather than inferred:

- Comics/cartoon detection literature exists but is about *character/panel/face* detection on manga/cartoon-character datasets, evaluated with *purpose-trained* CNNs, not zero-shot open-vocab transfer from photorealistic-trained models: [Manga109 comics annotations, Ogawa et al. 2018](https://arxiv.org/pdf/1803.08670) (panels, characters, text, faces — trained/evaluated within-domain, notes objects in comics are "highly overlapped compared to naturalistic images" which breaks some CNN assignment strategies); [iCartoonFace](https://arxiv.org/) style cartoon-face recognition (trained on cartoon faces from scratch, not transferred from natural-image detectors); [CoMix comic understanding benchmark, 2024](https://arxiv.org/html/2407.03550v2) and [Comics Datasets Framework, 2024](https://arxiv.org/html/2407.03540v1), both about consolidating comics detection datasets, not about open-vocab transfer performance.
- General open-vocab robustness papers exist for other domain shifts (aerial imagery, unusual street scenes, generated street-scene content) but none target flat-illustration/line-art: [Open-Vocabulary Detectors: Robustness Challenges under Distribution Shifts](https://arxiv.org/pdf/2405.14874), [Potential of Open-Vocabulary Models for Unusual Street Scenes](https://arxiv.org/pdf/2408.11221). These establish the *methodology* (evaluate a detector zero-shot on an out-of-training-distribution image style) that a cartoon-domain study would need, but no one has run it for cartoons/illustration as far as this search found.
- The oft-repeated claim that "photorealistic-trained detectors fail on line art/flat shading" has no direct primary-source benchmark evidence here for or against. The closest indirect evidence: Manga109-based comics detection work explicitly treats comics as a distinct domain requiring dedicated annotation and training rather than reusing natural-image detectors zero-shot, which is suggestive but not a controlled domain-gap measurement.
- Florence-2 ([Microsoft, MIT-licensed, weights open on Hugging Face](https://blog.roboflow.com/florence-2/)) supports an open-vocabulary detection/grounding task prompt within one unified model, but again no cartoon-domain evaluation was found.
- DETIC: no cartoon-domain evaluation found either; not pursued further past confirming this gap since the search budget was spent verifying the higher-priority questions.

**Bottom line:** treat any of these detectors' zero-shot cartoon performance as unverified and expect to spend real effort validating on your own scenes before trusting them as more than an auto-labeling bootstrap.

## 2. Tiling for many small objects in very large images (SAHI)

[SAHI (Slicing Aided Hyper Inference), Akyon et al., ICIP 2022](https://www.researchgate.net/publication/358603657_Slicing_Aided_Hyper_Inference_and_Fine-tuning_for_Small_Object_Detection); repo [obss/sahi](https://github.com/obss/sahi). Mechanism: slices the full image into overlapping tiles, runs the detector per tile, then merges tile-level detections back to full-image coordinates with NMS/greedy-merge across overlaps — model-agnostic, no retraining required ([SAHI quick-start docs](https://obss.github.io/sahi/quick-start/)).

Natively/documented-integrated detectors per the SAHI docs: **Ultralytics (YOLOv5/v8/v11), MMDetection, Detectron2, HuggingFace transformers detection models, TorchVision, Roboflow-hosted models, RT-DETR, and YOLO-World**. GroundingDINO, OWLv2, and Florence-2 are not in that native-integration list — using SAHI with them means using SAHI purely as a slicing/merging utility around a custom inference function, not the plug-and-play API.

Tile sizing: SAHI's own quick-start example defaults to `slice_height=512, slice_width=512` with `overlap_height_ratio=0.2, overlap_width_ratio=0.2` ([SAHI quick-start](https://obss.github.io/sahi/quick-start/)); the [Ultralytics SAHI guide](https://docs.ultralytics.com/guides/sahi-tiled-inference) shows the same 20% overlap convention. No primary source ties tile size to a specific target-object-size formula, so the practical rule of thumb — keep the tile close to the detector's native training resolution, and keep overlap ≥ the largest expected object so no bird is split across all tiles — is a reasonable-but-not-source-verified inference, stated as such. For GroundingDINO's ~800-1024px effective operating resolution, tiling a 4096px scene into a 5x5 or 6x6 grid with 800-1024px tiles and 20-25% overlap keeps each 100-250px bird at roughly the same apparent scale the detector saw in training, and 20-25% overlap (~160-250px) safely exceeds the largest bird size so no instance is fully bisected.

## 3. Fine-tuning small YOLO on a few hundred auto-labeled images

- **Dataset size:** [Ultralytics model-training-tips docs](https://docs.ultralytics.com/guides/model-training-tips) recommend "at least 1,500 images per class and a minimum of 10,000 instances per class" as a baseline — a few hundred auto-labeled scenes (each with 15-25 birds, so a few thousand bird instances) lands under the image-count guidance but can clear the instance-count guidance if scene count is on the high end of "a few hundred." Treat under-1,500-image training as workable-with-caution, not as meeting Ultralytics' own bar.
- **Split discipline:** Ultralytics' recommended baseline is roughly 70/15/15 train/val/test, split "by the right unit — scene, camera, day, location — not always by image" ([Ultralytics dataset-split guidance](https://academy.ultralytics.com/courses/dataset-readiness-for-yolo/split-the-dataset-correctly)). This directly matters here: if training crops are cut from the same source 4096px scene, crops from one scene must not be split across train and val, or the "no data leakage" check fails — [Ultralytics guidance flags surprisingly-good test performance as a leakage smell](https://docs.ultralytics.com/guides/model-training-tips).
- **Mosaic:** [Ultralytics data-augmentation docs](https://github.com/ultralytics/ultralytics/blob/main/docs/en/guides/yolo-data-augmentation.md) recommend mosaic for small-object detection and context learning, with the explicit caveat to use it "only if having partially occluded objects or multiple objects per image is acceptable and does not change the label value" — true here (birds don't change identity when occluded), so mosaic is appropriate; disable it near the end of training via `close_mosaic`.
- **HSV/color jitter:** the same docs describe `hsv_h`/`hsv_s`/`hsv_v` defaults as "a solid starting point" for natural imagery, but do **not** address flat-color/line-art domains where color is itself the label-discriminating signal. No explicit warning against color augmentation was found in the docs — this is an inference from the general Ultralytics principle that "augmentations you apply [should] reflect the same data distribution your model will encounter in production" ([same doc](https://github.com/ultralytics/ultralytics/blob/main/docs/en/guides/yolo-data-augmentation.md)). Practical implication for this project (not sourced, reasoned from that principle): reduce `hsv_s`/`hsv_v` jitter if bird species are color-coded, since shifting a red bird toward orange could plausibly blur the visual cue that distinguishes it from a background object.
- **Copy-paste:** documented in Ultralytics docs as a **segmentation-only** augmentation (`copy_paste` param, `flip`/`mixup` modes) — not applicable to a pure bounding-box detection task.
- **Auto-labeling pitfalls:** not addressed in Ultralytics' own docs directly; the general leakage/overfitting diagnostics above (val mAP plateauing while train loss keeps falling, or suspiciously strong val performance) are the documented tools for catching auto-label noise indirectly, but there's no Ultralytics-specific guidance for auto-labeled-data noise as a distinct problem.

## 4. SAM-family and exemplar-based few-shot detection/counting, offline on a 4090

| Model | License | Weights locally downloadable | Offline-capable |
|---|---|---|---|
| [CountGD](https://github.com/niki-amini-naieni/CountGD/) | MIT | Yes — `checkpoint_fsc147_best.pth` via Google Drive, plus dependency weights (Swin-B GroundingDINO checkpoint, ViT-H SAM from Meta, `bert-base-uncased`) all separately downloadable | Yes, once all four weight sets are cached locally; documented as tested on a single RTX 3090, no stated VRAM ceiling |
| [T-Rex2](https://github.com/IDEA-Research/T-Rex) | **"IDEA License 1.0"** — a custom, non-standard license, not Apache/MIT | **No.** The README requires an API key from `cloud.deepdataspace.com` for every example; there is no local-checkpoint code path in the repo. A stray Hugging Face weight link surfaced in search results but a live GitHub issue ([#99](https://github.com/IDEA-Research/T-Rex/issues/99)) shows a user hitting a 404 trying to download it, with no maintainer response — do not rely on that URL | **No — API-only** as currently documented. |
| [PerSAM / Personalize-SAM](https://github.com/ZrrSkywalker/Personalize-SAM) | Not stated in top-level search results — check repo `LICENSE` before use | Yes — training-free, built directly on downloadable SAM weights (ViT-H/L/B from Meta's SAM repo); PerSAM-F variant fine-tunes only 2 parameters in ~10s per exemplar | Yes, fully local given SAM weights are cached |
| Matcher (one-shot segmentation via SAM) | Not verified — not independently checked past the PerSAM search result mentioning it exists | Not verified | Not verified |

Note on CountGD's dependency chain: it is not a single checkpoint — it needs GroundingDINO Swin-B weights, SAM ViT-H weights, and BERT weights all present locally, which is more setup than a single-file YOLO checkpoint but all four components are open and unauthenticated to download per the repo's own instructions.

## API-only / license-restricted / unavailable-locally callout

- **T-Rex2 (IDEA-Research)** — API-only per the official repo README; requires an account and API key from `cloud.deepdataspace.com`; licensed under a non-standard "IDEA License 1.0," not a standard open-source license. Do not build a deterministic offline pipeline on this. A Hugging Face weights URL appears in some search summaries but a live, unresolved GitHub issue shows it 404s for at least one user — unverified and not to be relied on.
- **YOLO-World license** — conflicting signals in search results (GPL-v3 on the main repo vs. AGPL-3.0 on a related YOLOE project); re-verify the exact `LICENSE` file on the pinned commit before any use beyond internal experimentation, since GPL/AGPL carries copyleft obligations that MIT/Apache options (GroundingDINO, Florence-2, CountGD) do not.
- **Matcher** — license and local-weight-availability not independently verified in this pass; confirm before use.
- **No cartoon/illustration-domain benchmark exists** (per this search) for any of GroundingDINO/OWLv2/YOLO-World/Florence-2/DETIC — any claim about their cartoon-domain accuracy, including the "photorealistic detectors fail on line art" intuition, is currently unverified by a primary source and should be validated empirically on this project's own scenes before being trusted.
